01 What this repository is

The Amen API Integration Starter Kit is the official reference implementation of the Amen Platform API. It contains one small, working, copy-ready integration in every major technology stack, all built to the same layout and driven by the same reference scenario (a product escrow deal from creation to seller payout).

Use it as the model for your own integration instead of building from the raw API reference. Every client in the kit already handles the real-world details that are easy to miss — authentication, write protection, retries, timestamps and webhook verification — and every one of those behaviours has been confirmed against the live Amen sandbox.

Verified end to end. The reference scenario has been run in full against the real sandbox: a product deal was created, paid, executed, completed and paid out to the seller, and each step's webhook was received and its signature verified. The behaviours documented in section 6 and 7 are ground truth, not assumptions.

02 Set up your machine

You need three things before writing any code: the repository, a sandbox token, and the toolchain for your chosen stack.

Step 1 — Get a sandbox token

  1. Sign in to the sandbox dashboard: https://platform-sandbox.amnn.sa.
  2. Open Integrations → Public API and create a Public API account.
  3. Tick Enable REST API for that account (without it, every call returns 403 api_access__disabled).
  4. Copy the Secret key — this is your AMN_API_KEY. It is shown once.

Step 2 — Clone and configure

# clone the reference kit
git clone git@github.com:KMG411/amen-integration-starter-kit.git
cd amen-integration-starter-kit

# create your local environment file
cp .env.example .env

Edit .env and set your token. The default base URL is the sandbox — leave it until you are ready for production.

AMN_API_KEY=your-sandbox-secret-key
AMN_ENV=sandbox
# AMN_WEBHOOK_SECRET is only needed by the webhook receiver (section 7)
One .env per project. Each stack loads the nearest .env only. Keep your token in the kit's own .env; never commit it. .env is already git-ignored, and CI runs a secret scan (gitleaks) on every push.

Step 3 — Install your stack's toolchain

You only need the toolchain for the stack you are using — e.g. Python 3.11+, Node 20+, PHP 8.1+, JDK 17, .NET 8, Dart 3, or Swift 5.9. The exact install command per stack is in the next section.

A successful run walks a product deal through every state and prints the status after each step:

draft→ requested→ payment_pending→ paid→ executing→ executed→ completed→ payout
environment: sandbox (https://sandbox-api.amnn.sa) ✔ customers IC-000000032 (buyer), IC-000000033 (seller) ✔ deal D-0000000002 created → status=draft ✔ submit → requested ✔ approve → payment_pending ✔ pay with wallet → paid ✔ execution-start → executing ✔ execution-complete → executed ✔ complete → completed ✔ transfer-seller-amount → payout done 🎉 deal D-0000000002 finished: completed
If the run stops at payment_pending with a NEEDS_TOP_UP message, the sandbox wallet has no balance. Ask Amen support to top up the sandbox wallet, then re-run resuming from the deal number, e.g. python examples/01_golden_path.py D-0000000002.

05 The integration workflow

The recommended path from the reference kit to your own production integration:

1. Run the golden path proves your token + shows the lifecycle

Run examples/01_golden_path.py (or your stack's equivalent) against the sandbox until it completes.

2. Copy the client into your codebase MIT — copy freely

Copy the src/amen library (client, config, models, errors, resources, webhooks) into your project. It has few or no third-party dependencies by design.

3. Wire configuration to your secret store never hard-code tokens

Replace the .env loader with however your app supplies secrets (environment variables, a vault, your framework's config). Keep the token server-side.

4. Build your business flow from the resource methods reuse, don't reinvent

Compose customers.create, deals.create, deals.actions.* and the lookups into your product's flow. The lifecycle guard and retry logic come for free.

5. Add a webhook receiver section 7

Expose one HTTPS endpoint, verify every delivery, respond 200 fast, and do the real work asynchronously.

6. Test against the sandbox, then switch to live section 10

Point your integration tests at the sandbox, then flip AMN_ENV to live with a separate token when you go to production.

A minimal deal, in code

# Python — the same shape exists in every stack
amen = AmenClient()                        # reads AMN_API_KEY / AMN_ENV
buyer  = amen.customers.create(first_name="Buyer",  last_name="K", phone_code="SA", phone_number=...)
seller = amen.customers.create(first_name="Seller", last_name="K", phone_code="SA", phone_number=...)

deal = amen.deals.create(offer_type="product", offer_category=category_id,
                         offer_title="...", offer_price="100.00",
                         offer_delivery_fee="10.00")   # must be > 0 — see section 6
amen.deals.set_parties(deal.number, buyers=[buyer.number], sellers=[seller.number])
amen.deals.set_delivery_address(deal.number, city=city_id, district="...", ...)

amen.deals.actions.submit(deal.number)     # requested
amen.deals.actions.approve(deal.number)    # payment_pending
amen.deals.actions.pay_with_wallet(deal.number)   # paid (or pay_online for a checkout)

06 Real API behaviour you must handle

These behaviours are not obvious from the spec alone. They were confirmed by running real requests against the sandbox, and every client in the kit already handles them for you — this section explains what to preserve if you adapt the code.

BehaviourWhat it means & what the client does
Write protection (CSRF)The token alone is enough for GET, but POST/PUT/DELETE also need a double-submit token: a 32-hex value sent as both the X-CSRFToken header and the csrftoken cookie. The client generates one per instance and attaches it to every write.
Language headerLookup endpoints (categories, cities, dispute-reasons, cancel-reasons) return 500 with no Accept-Language header. The client always sends Accept-Language: en.
TimestampsDeal created_at/updated_at arrive as ISO-8601 strings from the REST API but as epoch-milliseconds inside webhook bodies. Parse defensively; don't assume one format.
Delivery fee > 0Creating a product deal with offer_delivery_fee: "0.00" is rejected as offer_delivery_fee__required — a zero fee is treated as missing. Send a positive value.
Money is a stringAll amounts are two-decimal strings in SAR ("100.00"). Never send floats.
Auth error codesA wrong environment or bad token returns 403 api_token__invalid (not 401); an account without REST enabled returns 403 api_access__disabled.
If you write your own HTTP layer instead of copying a client, the write-protection token is the detail most likely to bite you: a plain POST with only the API token returns 403 "CSRF cookie not set". Some HTTP libraries also strip manually-set cookies — the kit disables that where needed (for example .NET UseCookies=false, Swift httpShouldSetCookies=false).

07 Webhooks

Amen notifies your server of deal events by POSTing to a URL you register. Register once and store the secret it returns:

POST /api/v1/web-hooks/ { "url": "https://your-app/webhooks/amen" }
→ { id, url, secret_key }   # secret_key is shown once — store as AMN_WEBHOOK_SECRET

The signature scheme (verified against live deliveries)

Every delivery is signed. Amen signs the timestamp and the raw body together, Stripe-style — not the body alone:

signed_message = "{X-Webhook-Timestamp}" + "." + raw_body
X-Webhook-Signature: sha256=HMAC_SHA256(AMN_WEBHOOK_SECRET, signed_message)
HeaderMeaning
X-Webhook-EventEvent type, e.g. deal.status.changed (also present as event in the body)
X-Webhook-SignatureHMAC-SHA256 hex, sha256= prefixed
X-Webhook-TimestampISO-8601; part of the signed message — read it from the header

The body envelope is { event, timestamp, payload }, where payload is the full deal object; read payload.status for the new state.

Receiver rules

  1. Read the raw request body before parsing — re-serialising the JSON changes the bytes and breaks the signature.
  2. Verify the signature over timestamp + "." + raw_body with your secret, in constant time. Reject on mismatch.
  3. Respond 200 quickly; queue the real work asynchronously.
  4. De-duplicate — there is no event id, so key on the event timestamp (unique per delivery). Deliveries can repeat.
  5. Never trust the payload alone for money decisions — re-read the deal via GET /deals/{number}.

The kit's webhooks/ module implements all five rules; you pass it the request headers and raw body and handle the returned event.

08 Testing & continuous integration

Unit tests (offline)

Every stack ships fast unit tests that mock the network — encoding, error mapping, retry logic and webhook signatures (each asserts the same golden signature vector). Run them before every commit.

Integration tests (sandbox)

Mirror scenario/golden-path.yml and hit the real sandbox. They run only when AMN_API_KEY is set, so they never break an offline build.

What CI runs on every push

WorkflowPurpose
ciUnit tests for all 10 stacks in parallel, plus a gitleaks secret scan
sandbox-nightlyRuns the golden path against the live sandbox each night to catch drift
spec-driftWeekly check that the vendored spec still matches the published API
Before you open a pull request: run your stack's unit tests locally, keep the shared layout, and if you touch a client behaviour, update the matching test so the golden vector still passes.

09 Security best practices

  • Server-side only. The API token grants full account access. Never ship it in a mobile app, browser bundle, or public repo. Mobile and web front-ends must call your backend, which holds the token and calls Amen.
  • Use the proxy pattern for apps. The Flutter, Swift and Kotlin stacks include notes and a sample showing the client talking to your backend, not directly to Amen. Follow it.
  • Separate tokens per environment. Sandbox and live tokens are different and not interchangeable; a mismatch returns 403 api_token__invalid. Store them in a secret manager, not in code.
  • Verify every webhook. Treat an unverified delivery as hostile. Always check the signature (section 7) before acting.
  • Re-read before money moves. Confirm state with GET /deals/{number} rather than trusting a webhook payload or a stale local copy.
  • Keep secrets out of git. .env is ignored and CI scans for leaks — don't work around either.

10 Go-live checklist

  • Golden path completes end to end in the sandbox for your stack.
  • Your own deal flow works against the sandbox, including cancel and dispute paths.
  • Token is loaded from a secret manager, server-side only — never in client code or git.
  • A live token has been issued (separate from sandbox) and REST API is enabled for it.
  • Webhook endpoint is public over HTTPS, verifies signatures, and responds 200 quickly.
  • Webhook processing is idempotent (de-duplicates on the event timestamp).
  • Money decisions re-read the deal via GET /deals/{number}.
  • Errors are handled by code (see openapi/error-catalogue.md), with retries on 429/5xx.
  • AMN_ENV switched to live; integration tests pass against the sandbox in CI.
  • Monitoring/alerting is in place for failed payments, disputes and webhook errors.
When every box is ticked, switch AMN_ENV to live, deploy, and process a small real deal end to end as a final smoke test before opening the flow to customers.
