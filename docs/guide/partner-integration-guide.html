01 Start here

The Amen API Integration Starter Kit is Amen's official reference repository. It contains a small, working, copy-ready integration of the Amen Platform API in every major technology stack — all following one pattern and one reference scenario. Use it as the model for your own integration rather than starting from the raw API reference.

02 How an Amen integration works

Amen is an escrow service: the buyer pays into Amen, Amen holds the funds while the seller delivers, and releases them when the deal completes. Your platform creates the parties and the deal, drives the lifecycle through actions, and reacts to status changes.

The three objects you work with

Customer

A buyer or seller: name + phone. Identified by customer_number (e.g. CUST-0001). Create once, reuse across deals.

Deal

The escrow transaction: an offer (product or service), price, parties, addresses. Identified by deal_number. Has a status that only actions can change.

Account & wallet

Your merchant account: wallet balance (available / escrow / on-hold), linked bank accounts, withdrawals.

Deal lifecycle

draft ──submit──▶ requested ──approve──▶ payment_pending ──pay──▶ paid
                                                                  │
                                                        execution-start
                                                                  ▼
completed ◀──complete── executed ◀──execution-complete── executing
    │
    ├── transfer-seller-amount   (payout; status stays completed)
    └── dispute ──▶ disputed ──▶ dispute-approve → dispute_approved
                                └─▶ dispute-decline → completed
cancel: from draft, requested, payment_pending, paid, executing → canceled
payment_overdue: set by Amen when a payment_pending deal is not paid in time

Only draft deals can be edited or deleted. Submitting requires a buyer and a seller; product deals also need a delivery address. Every reference client checks these rules locally before calling the API and raises AmenLifecycleError with the allowed statuses — so you find ordering mistakes in development, not in production.

The reference scenario ("golden path")

1. Create buyer & seller→ 2. Create product deal→ 3. Parties + delivery address→ 4. Submit → Approve→ 5. Pay (wallet / online)→ 6. Execute → Complete→ 7. Payout to seller

Defined once in scenario/golden-path.yml; every stack's 01_golden_path example and integration test implement it step for step. Secondary scenarios (cancel, dispute, withdrawal) are in 02_… and 03_….

03 Your first deal in 10 minutes

  1. Get a sandbox token from the Amen platform and clone the kit: git clone https://github.com/KMG411/amen-integration-starter-kit.git
  2. Configure: cp .env.example .env and set AMN_ENV=sandbox, AMN_API_KEY=…
  3. Check the connection: curl -H "X-API-Token: $AMN_API_KEY" https://sandbox-api.amnn.sa/api/v1/account — you should see your account and wallet.
  4. Run the golden path in your stack (table in §1). Expected output:
environment: sandbox (https://sandbox-api.amnn.sa) ✔ customers CUST-0101 (buyer), CUST-0102 (seller) ✔ deal DL-000245 created → status=draft ✔ parties → status=draft ✔ delivery address → status=draft ✔ submit → status=requested ✔ approve → status=payment_pending allowed payment methods: [wallet, mada, visa_master, applepay] ✔ pay with wallet → status=paid ✔ execution-start → status=executing ✔ execution-complete → status=executed ✔ complete → status=completed ✔ transfer-seller-amount (payout) → status=completed 🎉 deal DL-000245 finished: completed
If the run stops at payment_pending with NEEDS_TOP_UP: the sandbox buyer wallet has no balance. Either top it up (bank details are in GET /api/v1/account → wallet.top_up_account) or complete the online checkout it created, then re-run the example with the deal number as an argument to resume from paid.
  1. Read the example you just ran — it is under 80 lines and is the pattern for your own code.
  2. Run the tests: unit tests are offline; integration tests repeat the golden path against the sandbox and skip automatically without a token.

04 Copying the reference into your codebase

The kit is deliberately small so you can lift it, not depend on it. Recommended approach: copy the src/amen folder of your stack into your project and adapt the three places that are yours to decide.

Copy as-is

  • AmenClient — one place for the token header, base URL, timeouts, and retry policy (only 429 and 5xx are retried, with jittered backoff and Retry-After).
  • Resources — customers, deals, deals.actions, withdrawals, webhooks, lookups, account, each mirroring one API tag.
  • Lifecycle guard — the ALLOWED_FROM table and the check before every action.
  • AmenApiError — parsed error codes with has(code).
  • Webhook verification + handler.

Adapt to your project

  • Configuration — replace .env loading with your secret manager (Vault, AWS/Azure/GCP secrets, Laravel config, Spring properties…). Keep the four variable names.
  • Logging — plug in your logger; never log X-API-Token or webhook secrets.
  • Persistence — store deal_number, customer_number and the last known status in your database; treat Amen as the source of truth and re-read on doubt.
  • Idempotency store — the handlers keep seen webhook ids in memory; back it with Redis or your DB in production.

Conventions to keep

TopicRule
MoneyAlways a string with two decimals in SAR: "1000.00". Never floats. The examples show the helper pattern.
TimestampsAPI values are epoch milliseconds; the models convert them to native date types.
IdentifiersUse number fields (DL-…, CUST-…, WR-…) in URLs and your own records; id is opaque.
PaginationList endpoints are paged. Use the iterAll / all() helpers rather than reading page 0 only.
Unknown fieldsAll models ignore unknown JSON fields, so additive API changes never break you. Keep that behaviour.
Mutating callsThe client sends Origin/Referer on POST/PUT/DELETE; keep it — the API applies origin checks.
Never put the API token in a mobile or browser app. It can be extracted from any binary or bundle. Mobile and dashboard front ends call your back end, which holds the token (see §8).

05 Payments

  1. After approve the deal is payment_pending. Call GET /deals/{n}/allowed-payment-methods/ to learn which methods apply: wallet, mada, visa_master, applepay.
  2. Wallet — POST action/make-payment-wallet. Synchronous: the deal becomes paid immediately if the buyer wallet has funds.
  3. Online (card / Apple Pay) — POST action/make-payment-online { "payment_method": "mada" } returns a Checkout (provider: hyperpay, hyperpay.checkout_id). Render HyperPay's checkout widget/SDK with that id in your UI. Amen marks the deal paid when the provider confirms — wait for the webhook or poll GET /deals/{n}.
  4. Service deals: pass the final price at approve time (price__required otherwise).
  5. Payout to the seller is explicit: action/transfer-seller-amount after completed. Withdraw your own available balance with POST /withdrawals/ to a linked bank account.
Deeper: docs/03-payments.md · examples 01_golden_path, 03_withdrawal

06 Webhooks

Register a URL once; Amen calls it on deal events. The reference receivers implement the five rules below — copy them exactly.

RegisterPOST /api/v1/web-hooks/ { "url": "https://your-host/webhook" } → { id, url, secret_key } Secretsecret_key is returned only at creation. Store it immediately as AMN_WEBHOOK_SECRET in your secret manager. If lost, delete and re-create the webhook. ReceiverEvery stack ships examples/04_webhook_receiver (Express, Flask-free stdlib, PHP built-in server, JDK HttpServer, ASP.NET minimal API, …) and a framework-agnostic WebhookHandler.

The five rules

  1. Read the raw body first. Verify the signature over the exact bytes received — never over a re-serialised object. (Express: express.raw(); Laravel: $request->getContent(); ASP.NET: copy Request.Body.)
  2. Verify, then parse. Reject with 401 on mismatch. The verifier accepts hex digests, optionally prefixed sha256=, and compares in constant time.
  3. Respond 200 quickly. Queue any real work; deliveries that time out are retried.
  4. De-duplicate by event id. Deliveries can repeat; the handler keeps a seen-set (back it with Redis/DB in production).
  5. Don't trust the payload for money decisions. On any event that matters, re-read the deal with GET /deals/{n} before updating your records.
// TypeScript — the same shape exists in every stack
const handler = new WebhookHandler(config.webhookSecret, async (event) => {
  const deal = await amen.deals.get(event.data.deal_number);   // re-read, then act
  await orders.updateStatus(deal.number, deal.status);
});
app.post("/webhook", express.raw({ type: "*/*" }), async (req, res) => {
  const { status, body } = await handler.handle(req.headers, req.body);   // raw bytes
  res.status(status).json(body);
});
Signature header and payload schema. The verifier's header name and algorithm are a single configuration point (SIGNATURE_HEADER / ALGORITHM in each stack's webhooks/verify), defaulting to HMAC-SHA256 of the raw body. Confirm the current values and event catalogue with the Amen integration team; docs/04-webhooks.md is updated as they are published.

07 Errors & retries

Errors are returned as { "error": ["code", …] }. Codes follow <field>__<problem> for validation and <object>__<problem> for business rules. The full catalogue (100 codes with recommended handling) is in openapi/error-catalogue.md.

ClassRetry?What to do
400 validation — first_name__required, offer_price__invalid, price__required…NoFix the request; surface field errors to the operator.
400 lifecycle — action not allowed for statusNoRe-read the deal; follow the lifecycle (§2). The local guard prevents most of these.
401 missing token · 403 api_token__invalidNoWrong or mistyped token, or sandbox token used against live (and vice-versa). Check AMN_ENV.
403 api_access__disabledNoAPI access is not enabled for the account — contact Amen.
404NoObject not found in this account/environment. Check the number.
429 rate_limit__exceededYesThe client backs off exponentially with jitter and honours Retry-After. Batch bulk work.
5xx / networkYesRetried up to 3 times by the client; then alert.
try { await amen.deals.actions.approve(dealNo); }
catch (e) {
  if (e instanceof AmenApiError && e.has("price__required")) askSellerForFinalPrice();
  else if (e instanceof AmenLifecycleError) refreshDealAndRetryLater();
  else throw e;
}

08 Mobile apps & web dashboards

Front ends never talk to amnn.sa directly. They talk to your back end, which holds the API token and uses one of the server-side reference clients.

Mobile / browser app ──(your session token)──▶ your back end ──(X-API-Token)──▶ api.amnn.sa
     Keychain · Keystore ·                    any server stack               escrow, payments,
     EncryptedSharedPreferences ·             from the kit                   webhooks
     flutter_secure_storage

iOS / Swift

Use swift/'s AmenClient on your server (Vapor/Hummingbird) or any other server stack. The app stores its own session token in the Keychain; see swift/SampleApp/README.md.

Android / Kotlin

Retrofit/OkHttp to your back end; session token in EncryptedSharedPreferences (Keystore-backed). Snippet in kotlin/sample-android/.

Flutter

flutter/sample_app shows the proxy pattern with flutter_secure_storage; flutter/amen_client is a pure-Dart package for your Dart back end or CLI.

Online payments from a mobile app

Your back end calls make-payment-online and returns the HyperPay checkout_id to the app; the app presents HyperPay's mobile SDK or web checkout with it. The back end learns the outcome from Amen's webhook and re-reads the deal.

Web dashboards (TypeScript / React / Next.js)

Put AmenClient behind a server route (/api/amen/* in Next.js route handlers, or an Express API) and have the React UI call that route. The typescript/ client is typed from the spec, so the same types flow through to the UI layer. Certificate pinning to your own host is optional but recommended for mobile.

09 Go-live checklist

  • Golden path and your own scenarios pass against the sandbox (integration tests green).
  • A live token has been issued; it lives in a secret manager, not in code, images or CI logs.
  • AMN_ENV=live is the only change between staging and production configuration.
  • Webhook registered against your production URL over HTTPS; secret_key stored; verification, de-duplication and re-read implemented.
  • Retries limited to 429/5xx; alerting on repeated 5xx and on webhook 401s.
  • Money handled as decimal strings end-to-end; timestamps converted from epoch-ms.
  • No API token in any mobile or browser artefact (grep your bundles).
  • Operators can see deal_number and status in your admin tools for support conversations with Amen.
  • You are subscribed to kit releases (CHANGELOG.md) so API changes reach you.

B Appendix — Postman, versioning & support

Postman

Import postman/Amen_API.postman_collection.json and the Amen — Sandbox environment; set apiToken. Requests are ordered to follow the golden path and capture customer_number, deal_number and webhook_id into environment variables, so the whole lifecycle can be run with the Collection Runner.

Versioning

The API base path is /api/v1. Kit releases are tagged v1.x.y; CHANGELOG.md records the spec date each release was validated against. A weekly job compares the vendored spec with docs.amnn.sa/openapi.yml and opens an issue on drift, so watch the repository to be notified of API changes early. Because clients ignore unknown fields, additive changes never require action.

Getting help

  • Check §10 and openapi/error-catalogue.md first — most questions are answered there.
  • Open an issue on the kit repository for anything about the reference code or documentation (include stack, deal number, and the error codes returned — never your token).
  • Contact the Amen integration team for account, token, wallet top-up and production questions.
